# Отчёт по домашнему заданию ДЗ-7
## «Поискать точки насыщения»

---

## 1. Цель работы

Найти точку насыщения сервера `dev.fp.big3.ru` на операции создания объектов (`04 Create Form`), используя профиль нагрузки с равномерно увеличивающимся количеством виртуальных пользователей (потоков).

**Точка насыщения** — это момент, когда сервер перестаёт справляться с нагрузкой: время ответа резко растёт, появляются ошибки, а производительность (throughput) перестаёт увеличиваться пропорционально числу пользователей.

---

## 2. Используемые инструменты

| Инструмент | Версия / Назначение |
|---|---|
| Apache JMeter | 5.6.3 |
| Плагин Stepping Thread Group | Профиль нагрузки «ступеньками» (от 1 до 20 потоков) |
| Плагин Response Times Over Time | График изменения времени ответа во времени |
| Плагин Transactions per Second | График скорости обработки запросов (throughput) |
| Плагин Active Threads Over Time | График количества активных виртуальных пользователей |
| Summary Report | Сводная таблица с итоговыми метриками |

---

## 3. Методика тестирования

### 3.1. Что тестировала
- Операция **создания объекта** (`04 Create Form`, POST-запрос).
- Сценарий включает вспомогательные шаги: логин, открытие реестра, получение позиции, логаут.
- Группы **Update** и **Delete** были отключены, чтобы не влиять на результат.

### 3.2. Профиль нагрузки (Stepping Thread Group)

| Параметр | Значение |
|---|---|
| Максимальное число потоков | 20 |
| Старт | 1 поток |
| Нарастание | +5 потоков каждые 5 минут |
| Удержание пиковой нагрузки | 5 минут |
| Общая длительность теста | ~27 минут |

Таким образом, нагрузка росла ступенями:
- **0–5 мин** → 1 поток
- **5–10 мин** → 6 потоков
- **10–15 мин** → 11 потоков
- **15–20 мин** → 16 потоков
- **20–25 мин** → 20 потоков (пик)
- **25–27 мин** → плавное снижение

### 3.3. Задержки в сценарии (таймеры)
- **~1 секунда** перед GET-запросами (переходы по ссылкам: Open Registry, Open Create Form, Get Position).
- **~4 секунды** перед POST-запросом `04 Create Form` (отправка формы создания).

## 4. Результаты тестирования

### 4.1. График «Active Threads Over Time» (активные потоки)

На графике видна «лестница» из пяти ступеней. Красная линия равномерно поднимается от 1 до 20 потоков, что подтверждает корректную работу профиля нагрузки. В конце теста наблюдается плавный спуск — все потоки завершились штатно.

> **Вывод:** профиль нагрузки отработал по плану.

---

### 4.2. График «Response Times Over Time» (время ответа)

На графике отображены два ключевых запроса:
- **Бирюзовая линия** — `04 Create Form` (создание объекта).
- **Тёмно-синяя линия** — `05 Get Position` (получение позиции).

**Наблюдения:**
- На первых ступенях (1–6 потоков) бирюзовая линия держится внизу — время ответа стабильно и невелико (около 100–200 мс).
- При переходе к **11 потокам** (интервал 10–15 минут) появляются **первые резкие всплески** — время ответа «взмывает» до нескольких секунд.
- На пиковых ступенях (16–20 потоков) пики становятся **регулярными и выше** — сервер уже не успевает обрабатывать запросы на создание в нормальном темпе.
- `05 Get Position` остаётся относительно стабильным — узкое место именно в операции **создания**.

> **Вывод:** резкий рост времени ответа на `04 Create Form` начинается при переходе от 6 к 11 потокам. Это первый признак насыщения.

---

### 4.3. График «Transactions per Second» (транзакции в секунду)

На графике видно:
- **Фиолетовые точки** — успешные `05 Get Position`.
- **Красные точки** — успешные `04 Create Form`.
- **Синие точки** — неуспешные (failed) `04 Create Form`.

**Наблюдения:**
- В начале теста транзакций мало (мало потоков).
- По мере роста потоков количество транзакций увеличивается.
- На правой половине графика (высокая нагрузка) появляются **синие точки (failures)** — сервер начинает отказывать в создании объектов.
- «Потолок» throughput для создания объектов достигается примерно на уровне 11–16 потоков; дальнейшее увеличение пользователей **не даёт пропорционального роста** успешных созданий.

> **Вывод:** скорость обработки запросов на создание перестаёт расти, а доля ошибок увеличивается — второй признак насыщения.

## 5. Анализ и определение точки насыщения

Сопоставим данные из всех источников:

| Количество потоков | Время ответа (Response Time) | Ошибки (Error %) | Throughput (TPS) |
|---|---|---|---|
| **1–6** | Стабильно, ~100–200 мс | Минимальные | Растёт пропорционально |
| **11** | Первые резкие пики | Начинают расти | Рост замедляется |
| **16–20** | Регулярные всплески до 2+ сек | ~50% | «Плато» — не растёт |

**Точка насыщения** определяется как момент, когда добавление новых виртуальных пользователей **перестаёт улучшать производительность** и начинает **ухудшать качество** ответов.

### 🎯 Итоговый вывод:

> **Точка насыщения сервера на операции создания объектов (`04 Create Form`) находится в диапазоне 10–11 виртуальных пользователей (потоков).**
>
> - До **6 потоков** сервер работает стабильно: время ответа низкое, ошибок мало.
> - При переходе к **11 потокам** (интервал 10–15 минут) наблюдается резкий рост времени ответа и появление ошибок.
> - При **16–20 потоках** сервер находится за пределами точки насыщения: половина запросов падает, время ответа непредсказуемо, throughput не увеличивается.

## 6. Рекомендации

1. **Для стабильной работы** рекомендуется ограничить нагрузку на операцию создания объектов **до 6–8 одновременных пользователей** (ниже точки насыщения).
2. **При 10+ пользователях** сервер требует оптимизации (улучшение производительности БД, кэширование, масштабирование).
